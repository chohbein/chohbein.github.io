Cartez Place recommendations for a live social map app: model, data pipeline and production serving. PyTorch · FastAPI · PostgreSQL (pgvector, PostGIS) · Supabase · Render

Cartez is a social map app where people save and share places they love. I co-founded it and built its recommendation system end to end, from raw training data to a live service inside the app.

It's a two-tower model. The place tower maps an 84-dimensional feature vector (category, a set of "vibe" tags, and normalized price, rating and review count) to a 128-dimensional embedding. There's no learned ID, so a place a user adds gets an embedding the moment it exists. The user tower averages the feature vectors of the places a user has saved and runs that through its own learned network into the same space. That trades some personalization for cold start, the right trade for a young app where most people have short histories: a user can get recommendations from a single save, with no retraining and no per-user parameters. Training used in-batch negatives, pulling each user toward places they liked and away from the rest of the batch.

A new app has no interaction data, so the model learned general taste from the UCSD Google Local reviews dataset. I treated four- and five-star reviews as stand-ins for saves and kept users with at least five, leaving 342M positive interactions from 16.2M users across ~2.6M places, and trained on a consumer GPU. At serving time the catalog narrows to the launch region.

The model runs as a FastAPI service on Render that embeds places as they're added, with embeddings stored in Postgres via pgvector on Supabase. Recommendations use PostGIS to restrict candidates to a radius around the user, rank them by vector similarity, and boost places real users added over entries seeded from the dataset, so the map favors the community over the starter catalog. A scheduled job refreshes each user's recommendation pool daily.

What I'd change: evaluation is the weakest part. Training loss beat the random in-batch baseline, but only modestly. Nearest-neighbor spot checks were coherent for places with rich tags (fast-food chains cluster together) and degenerate where features were thin: locations of the same chain have near-identical features, so they collapse to one embedding. There are no offline ranking metrics yet. Next is a held-out split measuring recall@k on users' saved places, then save-through rate on recommendations once the app has traffic.

News Aggregator Found when different outlets covered the same story, and summarized each one, daily. Python · AWS (EC2, Lambda, S3, RDS) · Selenium · Sentence-Transformers · PRIMERA · React

One event gets covered by CNN, Fox, AP, NPR and more, each with its own headline and framing. This system ran on its own every day: it scraped eight outlets, detected which articles from different outlets described the same event, and wrote one summary per story from the full text of every article, served through a React web app. I shut it down in 2025, when the scraping costs outgrew its use.

Every outlet needed its own Selenium scraper, run in parallel with one headless browser per site, handling infinite scroll, pop-up modals, a different date format on every site, and the same article appearing under several section URLs. A second pass pulled full article bodies for anything that landed in a story; paywalled outlets counted toward clustering but not summaries.

Clustering had no labels and no fixed number of stories per day, so I ran DBSCAN on Sentence-Transformer headline embeddings: it infers its own cluster count and leaves stories only one outlet covered out as noise. Raw similarity had a failure mode, though. One outlet's near-duplicate headlines, like live updates and cross-posts between sections, clustered with each other, producing "stories" with a single source. I fixed it by adjusting similarities before clustering: penalizing same-outlet pairs, and adding a small boost per shared keyword from a weighted ensemble of spaCy NER, KeyBERT and part-of-speech tagging.

For summaries I compared a reimplementation of Radev et al.'s centroid method, which extracts the sentences closest to a cluster's TF-IDF centroid, against PRIMERA, a transformer pretrained for multi-document summarization. ROUGE-2 against the source articles came out similar, but with no reference summaries for daily news that only measures overlap, so manual review decided it. Because the extractive method copies sentences verbatim, it also copied scraping noise: photo captions, "Getty Images" credits, promo headlines embedded in article bodies. PRIMERA wrote coherent prose. The centroid method was far faster, which didn't matter for a once-a-day batch job, so PRIMERA shipped.

The GPU only ran while it was needed. A CPU instance handled scraping, clustering and loading, then wrote cluster text to S3 and triggered a Lambda that started a GPU instance; that instance generated the summaries, wrote them back to S3, and shut itself down. Data loaded into Postgres through staging tables with idempotent inserts, so rerunning a day's job was safe.

What I'd change: clustering thresholds were tuned by inspection rather than measured, so next is labeling a few hundred headline pairs to report precision and recall. ROUGE can't catch a hallucinated summary, which calls for an NLI-based faithfulness check. And a scraper broken by a site redesign would fail silently; tracking article counts per outlet would flag it.

LLM-Powered Language Feedback API Schema-guaranteed grammar feedback on sentences in 8+ languages. Python · FastAPI · Anthropic Claude API · Prompt Engineering

A REST API that takes a sentence in a foreign language and returns structured grammar feedback. The hard requirement was that the response be machine-readable every time — a language-learning client can't handle a model that occasionally answers in prose — so I used Anthropic's tool-use interface to constrain output to a fixed schema rather than parsing free text and hoping.

The prompt work was the real effort: getting consistent, accurate feedback across 8+ languages including non-Latin scripts, where failure modes differ by language. Responses are cached in memory, since learners hit the same common sentences repeatedly. Tests cover multiple languages, error types, and edge cases including non-Latin scripts.
